# Web大富翁技术与体验设计

## 1. 项目目标

本项目是一款供约4名朋友游玩、最高支持6人的回合制联机大富翁游戏。首版只有一张44格方形地图，玩法遵循[华语简化版规则](./rules.md)。

首要目标：

- 对局规则清晰，所有玩家看到的资金、地产和回合状态始终一致
- 创建房间后可通过房间码快速加入，不要求注册账号
- 棋盘、动画、声音和操作反馈达到完整休闲游戏的观感
- 使用一套前后端统一的TypeScript代码，降低开发和维护复杂度
- 一个Node.js进程即可托管网页、房间和游戏状态

首版不考虑：

- 大规模并发、分布式部署和自动扩容
- 长期账号、好友、排行榜、商城和付费系统
- 数据库持久化及服务重启后的对局恢复
- WebRTC、主机迁移和玩家间直连
- 多地图编辑器、电脑玩家和观战系统

## 2. 技术选型

| 模块 | 选型 | 说明 |
| --- | --- | --- |
| 运行环境 | Node.js 24 | 同时运行构建工具和联机服务 |
| 包管理 | pnpm workspace | 管理前端、服务端和共享包 |
| 开发语言 | TypeScript | 游戏状态、规则和通信协议统一类型 |
| Web前端 | React 19 | 构建棋盘、玩家面板和操作界面 |
| 前端构建 | Vite 8 | 开发服务器和生产资源构建 |
| 服务端 | Fastify 5 | 提供少量HTTP接口并托管前端静态资源 |
| 联机通信 | Socket.IO 4 | 房间广播、操作回执、重连和状态恢复 |
| 数据校验 | Zod | 校验客户端命令及服务端消息 |
| 棋盘渲染 | Three.js + React DOM | 3D 棋盘与模型，DOM 承担行动和资料界面 |
| 动画 | 共享 RAF + 物理 worker | 棋盘按需渲染、骰子物理计算与 SVG 转盘 |
| 图标 | Lucide React | 操作按钮使用统一图标 |
| 状态存储 | 服务端内存 | 服务停止后房间消失，不引入数据库 |
| 图片资源 | PNG/WebP | 棋子、建筑、角落和特殊格插画 |
| 音频资源 | OGG/MP3 | 背景音乐及短音效 |

### 2.1 场景与界面分工

Three.js 渲染棋盘、城市、棋子、设施和道具；React DOM 渲染行动栏、资产、卡牌、竞拍及结果。`BoardScene` 只负责 React 生命周期，`BoardSceneController` 创建场景、投影状态并释放资源，`boardInput` 处理点击与拖动判别，`boardCamera` 计算镜头目标。

模型工厂、贴图与灯光延续原有实现。多个场景和行动播放共享一个 RAF，空闲不持续绘制，隐藏时暂停。

### 2.2 不使用第三方云数据库

房间数量少，游戏状态体积小，服务端内存足以保存全部对局。首版不引入Firebase、Supabase、Redis或关系型数据库。若未来需要服务重启后恢复对局，可增加SQLite定期保存房间快照，不改变现有通信结构。

## 3. 总体架构

```text
浏览器 React 客户端
        │
        │ Socket.IO命令与状态
        ▼
单体 Fastify + Socket.IO 服务
        │
        ├── 房间管理 RoomManager
        ├── 规则引擎 packages/game
        └── 内存状态 Map<roomCode, Room>
```

生产环境由同一个Node.js进程提供：

- `/`及静态资源：Vite构建后的Web页面
- `/health`：简单的服务状态接口
- `/socket.io`：联机长连接

客户端只负责展示和提交操作，服务端是唯一可信的游戏状态来源。

## 4. 服务端权威状态

客户端不能直接修改资金、骰子、地产、建筑或回合状态，只能提交命令：

```text
CREATE_ROOM
JOIN_ROOM
SET_READY
START_GAME
ROLL_DICE
CHOOSE_CARD
BUY_PROPERTY
SKIP_PURCHASE
UPGRADE_PROPERTY
SKIP_UPGRADE
MORTGAGE_PROPERTY
REDEEM_PROPERTY
SELL_BUILDING
PAY_JAIL_FINE
USE_JAIL_CARD
TRY_JAIL_ROLL
END_TURN
```

服务端收到命令后的处理顺序：

1. 用Zod校验消息结构。
2. 校验玩家身份、房间和当前回合。
3. 调用纯规则模块判断命令是否允许。
4. 在服务端生成骰子、洗牌或计算费用。
5. 更新游戏状态并增加`revision`。
6. 向操作玩家返回成功或错误回执。
7. 向房间广播动作事件和完整状态快照。

每条玩家命令携带唯一`commandId`。服务端记录近期已执行命令，避免重复点击或网络重发导致重复购买、升级或扣款。

## 5. 状态与消息设计

### 5.1 房间状态

```ts
interface RoomState {
  roomCode: string
  hostPlayerId: string
  phase: 'lobby' | 'playing' | 'finished'
  players: LobbyPlayer[]
  settings: RoomSettings
}
```

大厅状态包含昵称、棋子、座位、准备状态和房主。房主只能在2～6名玩家全部准备后开始游戏。

### 5.2 游戏状态与公开视图

`packages/game/src/types.ts` 是真实类型定义：内部 `GameState` 保存牌堆顺序和未揭晓卡牌；UI 接收独立 `GameView`。`packages/protocol/src/publicState.ts` 按明确字段生成公开快照，牌堆只有数量，待选卡只有决策编号、牌种、玩家和三个槽位。他人的密封报价替换为已提交标记。

仍广播完整快照，不引入增量同步。房间阶段由 `game === null` 与 `game.phase` 派生；成员连接状态由房间统一维护，并在输出时映射到游戏视图。

`engine/transitions.ts` 用带必需载荷的联合类型描述阶段进入，集中清理六类旧决策。底层存储保留原有可空字段以兼容规则查询，规则写入通过转换函数收拢。自选骰子的 `extraMove` 保留原行动阶段，所有后续结算完成后统一恢复；入狱、住院和出局终止额外行动。

### 5.3 动作事件

状态快照用于保证正确性，动作事件用于播放表现。一个动作可以产生一组有顺序的事件：

```text
DICE_ROLLED
TOKEN_MOVED
PASSED_START
PROPERTY_PURCHASED
PROPERTY_UPGRADED
RENT_PAID
CARD_DRAWN
PLAYER_SENT_TO_JAIL
PLAYER_BANKRUPT
TURN_CHANGED
```

事件包含`revision`。客户端只播放比当前已播放版本更新的事件；刷新或无法恢复事件时，直接用最新快照还原棋盘，不强制补播旧动画。

## 6. 房间与重连

- 创建房间时生成6位大写字母和数字组成的房间码
- 玩家加入后获得随机`playerId`和不可猜测的`reconnectToken`
- `reconnectToken`保存在浏览器本地存储中，不作为正式账号
- Socket.IO短暂断线恢复成功时继续接收遗漏消息
- 恢复失败或页面刷新时，客户端使用房间码和令牌重新加入并请求完整快照
- 掉线玩家的席位保留，棋盘显示掉线状态
- 当前玩家长时间无响应时，服务端执行保守操作：放弃购买、放弃升级或结束回合
- 房间内所有人离开一段时间后，服务端删除房间

首版不需要密码和正式鉴权。房间码用于发现房间，重连令牌用于认领原来的座位。

## 7. 前端结构

### 7.1 页面

- 房间页：创建房间、输入房间码、选择昵称和棋子
- 等候室：玩家座位、准备状态、房主开始按钮
- 游戏页：棋盘、玩家状态、当前操作、事件记录和设置
- 结算层：旅行战报、出局名次、趣味称号、可展开数据与重新开始

不制作营销落地页，打开应用后直接进入创建或加入房间界面。

### 7.2 棋盘与响应式布局

44 格棋盘通过 `worldRoute.ts` 映射到世界坐标。支持跟随棋子、全景和缩放；路线视图提供地点、所有者、费用与陷阱信息。点击地点直接打开详情；指针移动超过阈值不视为点击。

主界面使用三行布局：顶部导航、可伸缩棋盘区域、底部行动栏。棋盘区域内展示回合/玩家、场景及紧凑动态。资产、玩家、牌库和动态按需打开抽屉，手机保留主要行动与现金入口。

本人需要选择时展开决策，旁观者通过“查看”主动进入。资产详情沿用原抽屉，返回恢复列表上下文；道具包仅列持有道具，完整目录放在牌库。普通结果不使用阻断弹窗。

## 8. 视觉设计

### 8.1 设计方向

整体采用“现代实体桌游”风格：保留童年纸质棋盘、塑料棋子和小房屋的亲切感，同时使用更清晰的现代信息层级。

避免直接复制《MONOPOLY》的标志、角色、街道名称、棋子造型和插画。棋盘名称、角色、城市图形和卡牌文案均使用原创内容。

### 8.2 色彩

基础颜色建议：

- 棋盘纸张：偏白而非纯白，带轻微纸张纹理
- 正文和边框：炭黑或深灰
- 主要操作：清晰的绿色
- 警告和负向金额：红色
- 金钱及高价值提示：黄色或金色
- 机场和公用事业：分别使用青色、蓝色等功能色
- 地产组：使用8组容易区分且满足文字对比度的色带

界面不使用大面积单一紫色、深蓝或棕色主题，不使用装饰性渐变光球。颜色优先表达地产组、玩家身份和游戏状态。

### 8.3 字体与信息层级

- 棋盘地产名称使用紧凑清晰的无衬线字体
- 金额使用等宽数字特性，减少资金变化造成的跳动
- 玩家昵称和当前资金优先于资产统计
- 小格子内不使用大标题字号
- 字间距保持0，不随视口宽度缩放字体

### 8.4 美术资源

首版需要一套完整视觉资产：

- 6枚原创棋子或角色头像
- 1套1～4级房屋和旅馆素材
- 起点、监狱、医院、入狱四张角落插画
- 机场、电力公司、水利公司特殊格插画
- 机会和命运两种卡背及卡面装饰
- 纸张纹理、所有权旗帜和抵押印章

资产使用透明背景PNG或WebP。位图提供至少2倍显示尺寸，避免高分屏模糊。普通地产不需要22张完全不同的大图，可以使用区域色带、少量城市图标和统一版式保持完整感。

## 9. 动画系统

客户端维护独立的事件播放队列。服务端状态可以立即到达，但交互按钮在关键动画播放完成前保持锁定，避免动画表现落后于下一次操作。

时长定义在游戏包 `presentation.ts`，前端 `presentationTimings.ts` 复用：普通掷骰1850ms运动＋250ms点数确认，自选骰子400ms，短路径每格160ms，长路径480ms，入狱/送医600ms，炸弹1100ms。连续普通记录批量发布，不阻塞下一项操作。服务器创建新决策截止时间时使用同一展示时长预留动画预算。

逻辑事件进度和场景共用开始时间与共享 RAF。普通结果在紧凑播报与历史中展示，不再等待阅读计时；返回前台、重连或主动跳过时直接对齐最新状态。减少动态效果遵循系统偏好。

## 10. 声音设计

需要的基础音效：

- 骰子碰撞与落定
- 棋子逐格落下
- 纸币或硬币结算
- 地契盖章
- 房屋施工和旅馆升级
- 机场广播提示
- 电力与水流提示
- 机会、命运翻牌
- 监狱铁门
- 回合开始提醒
- 破产与胜利

对局菜单提供音效开关，偏好保存在本机。音效由现有音频模块按事件播放；本轮不增加背景音乐或混音面板。

## 11. 交互与可用性

- 当前玩家、当前阶段和下一步允许操作必须始终可见
- 购买、升级等决策同时显示操作后的剩余资金
- 地契详情展示购买价、抵押价、升级价和各等级收费
- 不能执行的按钮禁用，并提供简短原因
- 颜色不是唯一状态标识，玩家同时使用编号、头像或棋子形状
- 图标按钮提供工具提示和可访问名称
- 所有金额变化保留最近事件记录，方便玩家核对结算
- 网络断开、等待重连和恢复成功都有明确状态
- 对局主界面文案只服务于当前状态、行动选择及后果；不常驻“所有玩家可见”“已保存到动态”等功能介绍，也不重复解释界面上已有的按钮和数据
- 抽卡弹窗只展示牌堆名称、当前操作、卡背、序号与计时；牌堆统计留在牌库，超时后果只对当前操作者显示
- 完整规则按需展开，底价、余额、不可撤回和关键费用直接展示；普通结果不设置独立阅读控制

## 12. 性能策略

- 游戏内所有3D场景关闭实时阴影，保留方向光、环境光、材质高光以及原模型与文字精度。`ContactShadows.ts` 用椭圆/圆角接地投影统一表现建筑、棋子、道具和骰子；每个场景用一个 `InstancedMesh` 合并绘制，无阴影贴图、深度复制或额外阴影场景。棋盘文字在投影之后绘制，避免文字被压暗。
- `SceneRenderLoop.ts` 统一调度棋盘、骰子和 SVG 转盘指针，游戏画布与 SVG 动画共用一个RAF入口。稳定画面停止提交帧；玩家操作、状态更新、尺寸/可见性变化、异步物理轨迹完成会唤醒。页面隐藏和路线视图暂停绘制，返回时使用最新状态。
- 前景骰子/转盘在动画期间优先绘制；仍在运动的背景棋盘限制为15 FPS，稳定后停止。前景结束后棋子与相机动画恢复最高60 FPS。装饰船只、悬浮标记保持静态，减少动态效果偏好在运行时生效。
- 实景/路线切换保留棋盘实例，隐藏期间暂停渲染；再次显示时定位到最新玩家位置，避免重建所有地标、材质、文字贴图及WebGL上下文。
- 开发参数 `renderStats` 仅记录主场景提交耗时与绘制次数，阴影额外绘制为0；提交耗时不等于GPU执行时间或实测帧率。实际设备续航收益尚未测量。
- 棋盘格子数量固定，不使用虚拟列表
- 玩家状态更新时避免重新创建全部美术资源
- 图片使用WebP并按实际显示尺寸导出
- 音频在进入游戏后预加载，避免第一次播放延迟
- 棋子移动只动画`transform`，不动画布局属性
- React DOM 负责静态界面，3D 反馈通过共享 RAF 按需渲染
- 完整状态快照只包含数据，不包含重复的地契静态配置

## 14. 首版交付范围

首版应完整交付以下体验：

- 创建房间、房间码加入、准备和开始
- 2～6名玩家及6种不同棋子
- 一张精致的44格方形地图
- 掷骰、逐格移动、对子追加回合
- 地产购买、踩自有地产升级、收费和抵押
- 4个机场及2个公用事业
- 机会、命运、税收、起点、监狱和医院
- 资金不足处理、破产和胜利结算
- 短暂掉线恢复及刷新后重新加入
- 完整棋盘美术、核心动作动画和基础音效
- 桌面浏览器完整体验及移动端可操作布局

首版完成标准不是功能数量，而是一局游戏能够从创建房间顺畅进行到最终结算，过程中操作明确、状态可信、动画连贯且视听风格统一。

## 道具扩展的当前实现

- `board.ts` 按稳定地点 `id` 定义顺序，再生成运行时 `index`。44格、每边11步、12×12外框；卡牌目的地和3D城市模型按稳定地点查找。医院为左上角，南北机场前各有一个补给格，相隔22步；西侧新增开罗、东侧新增香港，普通地产共24块。
- `items.ts` 集中定义道具资料、可用条件和 `movementPreview`。服务器与自选骰子的落点预览使用相同路径拦截逻辑；路障/炸弹记录在 `GameState.hazards`，玩家持有道具及乌龟剩余次数 `turtleRollsRemaining` 记录在玩家快照，仅常规掷骰（`ROLL_DICE` 或 `ROLL_AGAIN`）扣减；道具额度 `itemUsedThisTurn` 仅在换玩家时重置，场上道具按 `ownerId` 限制每人一个。可用条件和放置限制的拒绝原因由共享函数提供给服务器和UI。
- 自选骰子以 `extraMove` 保存返回阶段和本次点数。所有购买、竞拍、卡牌、转盘、债务结算完成后在命令统一出口恢复原行动；入狱、住院、破产、换回合或游戏结束时清理。
- 监狱和医院共用离开流程与超时命令，通过 `isInJail` / `isInHospital` 区分地点和文案。普通到达医院只探访，炸弹或住院命运卡触发住院。
- `DiceValues` 支持一颗或两颗骰子；`DicePresentation`、`DiceScene`、物理模拟与 worker 均按骰子数量工作，保持全员统一的3D动画。
- 放置和触发事件携带道具快照，展示队列同步维护可见道具，使路障和炸弹按事件顺序出现、消耗。重连或返回实时状态时直接采用服务端快照。
- 路障和炸弹直接放在对应棋盘格内，可点击查看该格。炸弹触发时先移除模型，以共享的1100毫秒时长播放局部火花、烟尘和扩散环，再衔接送医移动，结果通过紧凑播报和历史说明。减少动态效果时只显示静态地面提示环；路线视图显示相应格子的触发提示。
- 用户提供的四宫格素材裁剪为 `public/assets/items/` 下的四张611×611图片，用于道具包、公共结果和历史；棋盘补给站与陷阱采用匹配现有世界的3D几何模型。

- `ExpansionLandmarks.ts` 提供开罗和香港的独立城市模型，补给站采用 `ItemModels.ts` 的棚亭模型；医院仍由 `CornerLandmarks.ts` 提供，旧 `scene=parking` 别名也指向医院。
- `ModelAssets.ts` 统一登记六个可交付模型，`ModelGallery.tsx` 和 `scripts/export-models.ts` 使用棋盘实际模型工厂生成预览与GLB，避免交付文件与场景脱节。图片预览由 `scripts/render-model-preview.mjs` 渲染导出。


## 卡牌扩充与整局统计（2026-09-11）

- `cards.ts` 维护各32张、明确 good/bad/neutral 分类的牌库。文案以旅行原因为主，`CARD_DRAWN.cardResult` 由引擎计算后保存到事件，金额、免付、补助替代、乌龟剩余次数、实际移动落点均为结算快照。
- `sourceCardId` 关联直接后果：卡牌赠道具、直接住院等不再生成第二个阅读弹窗；原始事件保留用于历史与统计。行动播报合并同次抽卡的直接结果，欠款、破产等后续决策仍单独显示。卡牌移动产生的新落点保持独立展示。
- `pendingCardProperty` / `WAITING_FOR_CARD_PROPERTY` / `CHOOSE_CARD_PROPERTY` 覆盖卡牌要求的城市降级，客户端和超时都通过同一候选函数。选择后回到统一行动出口，支持自选骰子的原阶段恢复；投降、破产、游戏结束清理选择。
- `statistics.ts` 在引擎提交事件时增量记录，`GameState.statistics` 与房间同步传输；不由客户端、短日志或传输事件重算。现金支付及破产余款事件携带 `tileIndex`，延期债务也保留地点。每个变更事件刷新最高身家，清算前额外保留峰值。
- 统计包含玩家固定计数、最多6人的往来、44格收入，以及固定大小的最大支付、最大竞拍节省、淘汰顺序。拒绝命令的克隆状态不会提交，重发命令不会重复记账。竞拍仅成交后计数，不泄漏未揭晓报价。
- `EndgameReport` 复用原头像、配色和原生模态框，不新增3D渲染。首屏名次和每人至多一项有效称号；玩家明细、至多3条名场面默认折叠。同值纪录显示并列，城市收入按地点聚合。
- DEV `?scene=game&result=1` 为带示例统计的战报美术预览；`?scene=game&card=卡牌ID` 使用实际引擎结算指定卡并展示真实组件。正式包不开放这两个预览入口。

命令重试沿用原编号；相同编号携带不同命令返回 `REQUEST_CONFLICT`。`TIMEOUT`、`DISCONNECTED`、`BUSY` 可重试，是否删除保存房间依据明确错误码，避免从中文提示推断控制行为。手动命令、竞拍/转盘到期和超时行动都通过同一个房间提交方法更新状态与截止时间。

`ROLL_AGAIN` 将对子后的继续行动与掷骰合并为一次原子命令；不重置道具额度或连续对子次数，不自动剥夺回合结束前的资产和道具操作。

## 节奏与批量筹款实现

- `FlatWheel.tsx` 使用 SVG 八格、灯珠红圈、中央开始按钮及顺时针指针。转盘专用 Three.js 场景、物理 worker 和碗面模型已移除；骰子物理与其他3D模型保留。指针角度使用服务端 `ballAngle`，奖励使用 `outcome`，每种效果仍占两格。
- 服务端按照房间最早截止时间安排可重新调度的计时器，替代每秒轮询；转盘到期仍由引擎校验3000ms边界。普通决策30秒、背面选卡和转盘启动15秒、筹款90秒、竞拍30秒。相同决策的成功操作保留原截止时间；新债务才获得新的筹款预算。
- `LIQUIDATE_ASSETS` 携带不重复的 `{ tileIndex, sellLevels, mortgage }` 列表。`liquidationQuote` 由前后端复用，先校验全部资产和足额付款条件，再在同一次命令克隆状态中出售、抵押并复用 `settleDebt`。任何错误返回原状态；命令编号沿用现有幂等机制。
- 地产购买、升级按钮固定于操作栏，旁侧地产摘要不再以强制模态框隔断棋盘。仍由玩家确认结束回合，保留行动后的道具和资产操作机会。

- 路障与炸弹命令均显式携带 `tileIndex`。`itemPlacementOptions` 统一生成脚下及前后两格的五个候选格；`itemPlacementBlockReason` 同时供面板和引擎校验范围、已占用格与每人场上道具上限。放置本身不触发，仍由移动路径结算触发。
